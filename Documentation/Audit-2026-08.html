Modern Dev Tools — Quadruple-Pass Audit

Performance · caching · IMGUI/VRAM · mod interoperability · new capabilities
Target: astryl.ModernDevTools v1.2 · 49 C# files, 8,797 LOC · RimWorld 1.6 / Unity Mono net472
Method: full static read of every source file, cross-checked against decompiled Assembly-CSharp, HugsLib.dll and ArchotechLogs.dll. No changes made. Nothing measured at runtime.
Headline. The architecture is sound — the analysis pipeline is correctly cached (ConditionalWeakTable per message), the index builds are prewarmed off-thread, and row culling already exists in the log list. The problems are concentrated in three places: (1) per-frame recomputation of things that never change while a message stays selected; (2) the knowledge base has no viewport culling at all; (3) replacing the vanilla log window silently deletes the log-window UI of HugsLib (active, load order #19) and Archotech Logs. Finding R1 is, in my judgement, the single most important item in this document — larger than any performance item.

On VRAM: there is essentially nothing to reclaim. Verified below — the entire suite draws from one shared engine texture. The right target is CPU-side IMGUI work, not GPU memory.

1.4 "Missing libraries"

I checked for genuinely absent infrastructure rather than assuming a package is needed.

  • JSON: the hand-rolled Source/Community/Json.cs (146 LOC) is the correct call. RimWorld ships no JSON library and adding Newtonsoft would mean shipping a DLL and inviting assembly-version conflicts. Keep as-is
  • Harmony: correctly referenced with ExcludeAssets="runtime" and declared as a mod dependency — 0Harmony.dll is not shipped. Correct
  • Genuinely missing (internal): a shared TextMetrics memo cache keyed on (string, width, font, fontSize, wordWrap). Its absence is the direct cause of P1–P5. This is the one piece of "framework" the mod actually lacks. Build it
  • Genuinely missing (internal): a per-analysis derived-data cache hanging off LogAnalysis (impact result, glossary terms, measured heights). Also the direct cause of P2–P4. Build it

1.5 "Multi-polling ticks"

Clean. The mod registers no GameComponentTick, MapComponentTick or ThingComp tick. GameComponent_ModSnapshot is event-driven, not polled. There is no tick-rate cost at all when no window is open. The per-frame cost is entirely OnGUI-scoped and therefore only paid while a dev window is visible — which is the right design. The one exception is B4 below: three Harmony hooks that do run every frame regardless.

1.6 Correctness and robustness defects

#SiteDefectCert.
B1KnownIssueIndex.EnsureBuilt Publishes _all = new List<Compiled>() then fills it, with no lock. The startup prewarm runs this on a background thread. A main-thread caller arriving mid-build sees _all != null, returns immediately, and iterates a list being mutated → either a swallowed InvalidOperationException (the try/catch in Match hides it) or a partial library. Symptom: an error inspected right after launch silently gets no diagnoses. Build into a local, assign under a lock — exactly the pattern HarmonyIndex.Build() already uses correctly.90
B2SettingsPage.Draw No try/finally around Palette.BeginScroll/EndScroll. Every other call site pairs them correctly. If DrawContent throws, GUI.skin.verticalScrollbar* stays swapped globally and BeginScrollView is left unbalanced — corrupting every vanilla scrollbar for the rest of the session. Compounded by the known engine behaviour that a throwing window is force-closed by WindowStack, so the user sees settings vanish and every scrollbar go flat.97
B3Palette.BeginScroll Saves the previous skin into single static fields, not a stack — it is not re-entrant. Today no call site nests, so it works. But ErrorModule.DrawSection is invoked inside the inspector's active scroll view, so the first third-party module that calls Palette.BeginScroll corrupts the restore. This is an API-surface hazard, not just a latent bug.95
B45 hardening patches Both hardening features default to off, yet the patches are always installed: a finalizer on Window.WindowOnGUI (runs for every window, every pass), a postfix on WindowStack.WindowStackOnGUI (every frame), a postfix on Log.Error (every error in the game), and three map/world OnGUI finalizers. A guard clause makes the body free; it cannot make the dispatch free, and a finalizer additionally forces the target into a try/catch. Move to settings-driven Patch/Unpatch, or at minimum a Prepare() gate.96
B5CommunityData background thread Parsed dictionaries are published through volatile reference assignment — correct. But the finally block calls LogAnalysisCache.Clear() off-thread, replacing a static field a main-thread GetValue may be using. Benign in practice (worst case one stale analysis) but worth a main-thread marshal for hygiene.70

Pass 2 — IMGUI usage, and the VRAM question answered

Direct answer: there is no meaningful VRAM to save, and no lower-VRAM alternative exists that preserves the aesthetic. The premise does not hold for this mod — and that is good news.

2.1 What the suite actually costs on the GPU

Verified against decompiled Verse.Widgets:

// Verse/Widgets.cs:827 - the primitive behind every solid fill in the suite
public static void DrawBoxSolid(Rect rect, Color color) {
    Color prev = GUI.color;
    GUI.color = color;
    GUI.DrawTexture(rect, BaseContent.WhiteTex);   // ONE shared texture, tinted by GUI.color
    GUI.color = prev;
}

// Verse/Widgets.cs:844 - a 1px border is FOUR separate draws of that same texture
public static void DrawBox(Rect rect, int thickness = 1, Texture2D lineTexture = null) {
    GUI.DrawTexture(...left...);  GUI.DrawTexture(...right...);
    GUI.DrawTexture(...top...);   GUI.DrawTexture(...bottom...);
}

Consequences, all verified:

  • Colour is a GUI.color tint, not a texture. The palette's ~14 colours allocate zero textures.
  • Total GPU residency owned by this mod: 3 shipped icons (Pin, Chevron, Close) plus three 2×2 textures created in Palette.InitScroll via SolidColorMaterials.NewSolidColorTexture. That is a few kilobytes. There is no atlas, no render texture, no material churn, no per-frame allocation.
  • Therefore every "reduce VRAM" technique — atlasing, compression, texture pooling, render-texture caching — targets something that does not exist here. Two of them would increase VRAM.
The real cost is Palette.DrawCard = 5 draw calls (1 fill + 4 border edges), and the card is the mod's dominant primitive. Static count across the codebase: 101 call sites of DrawBoxSolid/DrawBox/DrawCard/DrawWell.

3.2 R1 HugsLib — the biggest compat liability

HugsLib is active in this modlist at load order #19. Decompiling HugsLib.Logs.LogWindowExtensions confirms it exposes a public, XML-documented extension API that is the community's de-facto standard for adding buttons to the debug log: 
public static void AddLogWindowWidget(WidgetDrawer drawerDelegate,
                                     WidgetAlignMode align = WidgetAlignMode.Left);

public delegate void WidgetDrawer(Window logWindow, Rect widgetArea,
                                  LogMessage selectedLogMessage, WidgetRow widgetRow);
It is rendered by HugsLib.Patches.EditWindow_Log_Patch, a prefix on EditWindow_Log.DoMessagesListing.

What breaks. Modern Dev Tools prefixes UIRoot.CheckOpenLogWindow and DebugWindowsOpener.ToggleLogWindow and returns false unconditionally. The auto-open path, the dev-toolbar button and the hotkey are the only ways vanilla opens EditWindow_Log. With our mod active, EditWindow_Log is never constructed, so DoMessagesListing never runs, so DrawLogWindowExtensions never runs. Silently lost:

  • HugsLib's "Share logs" button (LogPublisher) — the single most-used log feature in the RimWorld support ecosystem. Every "post your HugsLib log" support request now fails.
  • HugsLib's "Files" menu (open Player.log / save dir / mods dir).
  • HugsLib's "Copy" button.
  • Every third-party widget any other mod registered through AddLogWindowWidget.

No error, no warning, no message. The user simply concludes HugsLib broke. This is doubly notable because the Schematic records a deliberate decision not to clone HugsLib's log upload — correct on its own terms, but it assumed HugsLib's own button would still be reachable. It is not. Certainty 98

Pass 4 — New capabilities

4.1 N1 Intercepting repeating log entries — yes, and there is a real gap to close

Verified against decompiled Verse.Log and Verse.LogMessageQueue. Four facts drive the design:

// Verse/Log.cs - Error(), Warning() and Message() all share this shape
lock (logLock) {
    messageQueue.Enqueue(
        new LogMessage(type, text, StackTraceUtility.ExtractStackTrace()),  // (1) ALWAYS runs
        out var repeatsCapped);                                            //     even for repeat #500
    if (repeatsCapped) return;                                             // (2) cap is 99
    ...
}
Debug.LogError(text);   // (3) Unity -> synchronous Player.log write, until the cap

// Verse/LogMessageQueue.cs - (4) dedupe compares against lastMessage ONLY
if (lastMessage != null && msg.CanCombineWith(lastMessage)) { ... }
  1. StackTraceUtility.ExtractStackTrace() is evaluated before the dedupe test. Every repeat pays a full managed frame walk plus a large string allocation. On Mono this is expensive, and it is unavoidable through vanilla's own path. new LogMessage additionally does DateTime.Now.ToString(...) per call.
  2. The repeat cap is 99. Below it, every occurrence also does a synchronous Debug.Log* → Player.log disk write.
  3. All of it is inside lock (logLock), so tick-loop spam serialises through one lock.
  4. The gap: dedupe only compares against lastMessage — it is strictly consecutive. Two interleaved errors (A, B, A, B…) never combine, so they never reach the cap, never stop writing to disk, and permanently churn the 1,000-entry queue. This is the common real-world case: one broken pawn producing two errors per tick.

Proposed design — "Throttle repeating log spam" (toggleable)

Prefix on Log.Error(string) / Log.Warning(string) / Log.Message(string):

  1. If the feature is off  -> return true  (vanilla, untouched)
  2. key = FNV-1a(text) + type            // no ToLower, no substring, zero allocation
  3. Look key up in a fixed 64-slot ring of {hash, count, firstFrame, lastFrame}
  4. count < Threshold (default 5)        -> return true   // first occurrences ALWAYS pass
  5. count >= Threshold, within window     -> count++; return FALSE
        skips: ExtractStackTrace, LogMessage alloc, Debug.Log*, Player.log write,
               TryOpenLogWindow, and the pause-on-error tick pause
  6. Every N suppressed (or on a timer) emit ONE summary line so nothing vanishes silently
  7. Surface "suppressed x N" on the message in our inspector + impact banner
AspectAssessmentCert.
Mechanism worksA Harmony prefix returning false on Log.Error(string) demonstrably skips the whole body. Log.ErrorOnce routes through Error, so it is covered too.92
Closes a real vanilla gapThe interleaved-spam case is genuinely unhandled by vanilla, and our ring buffer handles it. This is the part that is new, not just cheaper.95
